Extending bmdx-core beyond genomics to support arbitrary toxicology data domains

1. What This Project Is

BMDExpress 3 is a dose-response modeling tool used across NIEHS, EPA, and the broader toxicology community. Today it only handles gene expression data. We are extending it to handle any toxicology data domain — clinical chemistry, organ weights, hematology, histopathology, and more — through configuration rather than code.

Why now: The 5dToxReport project (rlm-bmdx) already pushes apical endpoint data through BMDExpress’s .bm2 format, but the integration is fragile. Domain identity is guessed from filenames. Metadata fields are null and must be inferred by an LLM. The genomics terminology in the API creates constant friction for team members working with clinical data.

End state: A new data domain (e.g., coagulation, urinalysis) is added by writing a YAML configuration file. No Java code changes. No developer involvement beyond review.

Resource impact

8 phases. Phases 1–2 are low-risk and already underway. Phase 6 (annotation abstraction) is the most complex and may require dedicated design time. New domain rollout (Phase 8) can be done by SMEs writing config files.

BMDExpress 3’s data model is genomics-specific: Probe, ProbeResponse, ChipInfo, ReferenceGeneAnnotation, CategoryAnalysis. The core abstraction — DoseResponseExperiment — is domain-neutral in concept but genomics-specific in API surface.

We are introducing a domain-agnostic layer through interfaces, aliases, and a YAML-driven configuration system. The approach preserves full backward compatibility with existing .bm2 serialization while making the API bilingual (genomics callers keep working; new code uses domain-neutral names).

Key constraint: Jackson serialization format must not change. Existing .bm2 files must deserialize without modification across all BMDExpress 3 versions.

We are refactoring the bmdx-core data model so that genomics-specific class and method names have domain-neutral alternatives. This is being done incrementally — new interfaces and alias methods, not renames — so nothing breaks.

The work happens on the bmdx-core branch, which is the headless library version of BMDExpress 3 (132 source files, no GUI). Prior work on the llm-metadata branch added ExperimentDescription with controlled vocabularies from vocabulary.yml.

BMDExpress 3 is being extended to support data domains beyond gene expression. The first phase (terminology aliasing) adds new interfaces and methods alongside existing ones. No existing behavior changes. Your primary concern is verifying that nothing regressed — .bm2 files still load, existing API calls still work, and new alias methods return identical results.

BMDExpress 3 currently only supports gene expression dose-response data. We are extending it to support the full range of toxicology endpoints you work with in NTP/NIEHS studies:

  • Clinical chemistry — ALT, AST, glucose, BUN, creatinine, bilirubin, cholesterol
  • Hematology — RBC, WBC, hemoglobin, hematocrit, platelets, differential counts
  • Organ weights — absolute and relative (to body weight / brain weight)
  • Body weights — terminal, interim, and gain
  • Histopathology severity scores — ordinal grading (0=normal through 4–5=severe)
  • Urinalysis — specific gravity, pH, protein (dipstick), glucose
  • Coagulation — prothrombin time, APTT, fibrinogen
  • Neurobehavioral — functional observational battery (FOB), motor activity, grip strength
  • Reproductive/developmental — implantation sites, litter size, fetal weights, malformations
  • Toxicokinetics — Cmax, AUC, t½

Each domain will be defined by a configuration file that captures the domain’s scientific characteristics: what endpoints exist, what units they use, which direction is adverse, what reference ranges apply, and how endpoints group into organ systems. Your expertise is needed to validate these configurations.

Phase 1 complete (2026-03-09)

Terminology aliasing layer is in place. New interfaces (Endpoint, EndpointResponse), alias methods on DoseResponseExperiment and IStatModelProcessable, @JsonAlias for deserialization compatibility, @Deprecated on genomics-specific names.

Jackson round-trip hardening: Added @JsonIgnore to prevent Jackson from serializing redundant computed properties that break deserialization:

  • ExperimentDescription — 7 computed getters (getColumnHeaders, getColumnValues, getExperimentType, isInVivo, isInVitro, getStatusBarString, getFormattedString). These used Arrays.asList() (fixed-size list) which caused UnsupportedOperationException during deserialization.

JSON → .bm2 round-trip proven: JsonToBm2.java (in rlm-bmdx) reads Jackson-annotated BMDProject JSON and writes canonical .bm2 via ObjectOutputStream. This closes the metadata loop: LLM-inferred metadata → user review → JSON → .bm2 → BMDExpress 3 can consume.

3. Domain Configuration

The central idea: each toxicology data domain is described by a YAML file that the framework reads at startup. Adding a new domain means writing a config file — not modifying Java source code. This makes the system extensible by anyone who understands the science, not just developers.

Decision needed: config ownership

Should domain configs ship inside the JAR (curated, versioned with the software), or be loadable from an external directory (user-contributed, lab-customizable)? Recommendation: ship defaults in the JAR, allow overrides from an external directory.

Each domain config declares everything the framework needs to handle that data type: import format, applicable statistical methods, endpoint schema, grouping hierarchy, and reference ranges.

domain: clinical_chemistry
display_name: "Clinical Chemistry"
response_type: continuous

endpoint_schema:
  id_format: name
  unit_field: unit

platform: "Clinical Endpoint"
provider: "Clinical Endpoint"
adverse_direction: endpoint_specific
adverse_direction_map:
  "ALT": increase
  "Albumin": decrease
analysis_unit: animal
dose_metric: mg/kg/day

import:
  format: long
  required_columns: [animal_id, dose, endpoint, value]

prefilters:
  available: [williams_trend, dunnetts, anova]
  default: [williams_trend, dunnetts]

bmd_models:
  available: [hill, exponential, power, poly2, poly3]
  default: [hill, exponential, power, poly2]

grouping:
  levels:
    - name: endpoint
      source: identity
    - name: organ_system
      source: organ_map.yml

reference_ranges:
  source: historical_controls.yml
Risk: response_type polymorphism

Some domains (urinalysis, neurobehavioral) have mixed response types — continuous for some endpoints, ordinal for others. The config may need per-endpoint response_type overrides, not just a single domain-level declaration. This complicates model gating logic.

Domain configs are YAML files loaded by a DomainRegistry singleton (similar pattern to VocabularyConfig). Each config maps to a DomainConfig POJO deserialized by Jackson YAML.

The ExperimentDescription.domain field (Phase 2) links an experiment to its config. Access pattern:

ExperimentDescription desc = experiment.getExperimentDescription();
DomainConfig config = DomainRegistry.get(desc.getDomain());

// Gate prefilters by domain
List<String> prefilters = config.getPrefilters().getAvailable();

// Check adverse direction for an endpoint
String direction = config.getAdverseDirection("ALT"); // "increase"

Config files go in src/main/resources/domains/ and are loaded from the classpath. External overrides (future) would check a user directory first.

Domain configuration is planned for Phase 3. When it arrives, key test scenarios:

  • Valid config loads without error
  • Missing config file → graceful fallback (not a crash)
  • Malformed YAML → clear error message identifying the problem
  • Unknown domain value in an experiment → treated as generic/unrecognized
  • Config with unknown fields → ignored (forward compatibility)
  • Each shipped domain config round-trips: load → serialize → reload → identical

4. Structural Challenges

Six design challenges go beyond simple renaming. Most are solvable with the domain config approach, but two deserve attention:

High risk: Annotation/grouping abstraction (Phase 6)

GO term and pathway analysis is deeply embedded in the codebase. Making it pluggable (so clinical data can group by organ system, histopath by tissue, etc.) is the most architecturally complex change. All other phases can proceed independently.

Medium risk: Reproductive/developmental data (Phase 8)

This is the only domain where the analysis unit changes from individual animal to litter. The nested structure (dam → litter → pups) may require framework-level changes beyond what a config file can express.

Response type

Not all dose-response data is continuous. The domain config declares response_type: continuous | ordinal | dichotomous | count, which gates applicable BMD models and prefilters. BMDExpress has dichotomous modeling ancestry from EPA BMDS — needs assessment of what’s still functional in bmdx-core after the GUI strip.

Analysis unit

Reproductive data is per-litter with nested observations. Config declares analysis_unit: animal | litter. Framework handles aggregation. This may require a new data structure (litter-level experiment) rather than just configuration.

Adverse direction

Per-endpoint directionality affects BMD model selection (one-sided vs two-sided fitting). Config carries adverse_direction_map with per-endpoint overrides.

Endpoint hierarchies

Genomics: gene → gene set → pathway. Clinical: endpoint → organ system → systemic effect. The grouping scheme is declared per-domain with external mapping files. Phase 6 abstracts ReferenceGeneAnnotation and CategoryAnalysis into pluggable interfaces.

Dose metric

mg/kg/day (oral), mg/m³ (inhalation), mg/cm² (dermal). Config-declared, flows into BMD reporting.

Reference ranges

Historical control data enables pre-modeling QC (flag outliers), adverse direction inference, and BMD context assessment. Config points to an external data file.

Structural challenges mostly affect future phases. For now, be aware that Phase 5+ will introduce domain-dependent behavior — the same operation may produce different results depending on the domain config. Test matrices will need to cover multiple domains.

The highest-risk area for regression is Phase 6 (annotation/grouping), where the GO term pipeline gets abstracted. Gene expression analysis must produce identical results before and after.

Several scientific questions need your input as we design the framework:

Response types

We need to correctly categorize each domain’s data type, because different statistical models apply:

Data typeExamplesModels
ContinuousBody weight, ALT, organ weightHill, exponential, power, polynomial
OrdinalHistopathology severity (0–5)Ordinal logistic, proportional odds
DichotomousTumor incidence (yes/no)Logistic, probit, log-logistic, multistage

Question: Some domains have mixed types (e.g., urinalysis has continuous specific gravity AND semi-quantitative protein dipstick). Should we handle these as one domain with per-endpoint types, or split into sub-domains?

Endpoint groupings

We need scientifically validated mappings of endpoints to organ systems. For example:

  • ALT, AST, ALP, bilirubin, albumin → Hepatic
  • BUN, creatinine → Renal
  • Glucose, cholesterol, triglycerides → Metabolic
  • RBC, hemoglobin, hematocrit → Erythroid
  • WBC, lymphocytes, neutrophils → Leukocyte

Do these groupings match your conventions? Are there endpoints that belong to multiple systems?

Adverse direction

For each clinical chemistry and hematology endpoint, which direction of change is considered adverse? Some are obvious (ALT ↑ = hepatotoxicity), others are context-dependent (glucose can be adverse in either direction). We need a complete mapping.

5. Downstream Impact

The 5dToxReport web application (rlm-bmdx) is the primary downstream consumer. As bmdx-core becomes domain-aware, rlm-bmdx sheds workarounds:

  • No more guessing domain from filenames
  • No more LLM-based metadata inference (populated at import time)
  • No more Python-side data format conversion
  • Single export path instead of separate genomics vs apical code

This reduces maintenance burden and eliminates a class of bugs caused by incorrect domain inference.

Metadata loop closed (2026-03-09)

rlm-bmdx now captures experiment metadata via a review UI with controlled vocabulary dropdowns (species, strain, sex, organ, platform, etc.). After user approval, metadata is written back to integrated.json and re-exported to integrated.bm2 via JsonToBm2. BMDExpress 3 can consume this .bm2 with metadata pre-populated — closing the loop even for file pools that started with no .bm2 files.

The key file to watch: experiment_metadata.py. Once bmdx-core populates experimentDescription natively at import time (Phase 3), the LLM-based metadata inference becomes unnecessary for domains with configs.

What’s already built in rlm-bmdx

As an interim solution (until bmdx-core has native primary metadata capture), rlm-bmdx now handles the full metadata lifecycle:

  • LLM inference: experiment_metadata.py infers species, strain, sex, organ, platform, etc. from experiment names and file context
  • User review: Metadata review UI with controlled vocabulary dropdowns, species→strain filtering, and per-experiment editing
  • Approval: User explicitly approves metadata, which writes metadata_approved.json marker
  • .bm2 export: JsonToBm2.java writes integrated.bm2 with approved metadata baked in
  • Pool reset: POST /api/pool/reset/{dtxsid} provides a clean slate — removes all files, integrated data, metadata, and approved sections while preserving chemical identity and version history

Downstream impact is gradual. Each phase in bmdx-core enables removing a workaround in rlm-bmdx, but the workaround continues to function until explicitly removed. No forced migration.

Key regression risk: when rlm-bmdx switches from its own domain inference to reading bmdx-core’s native domain field, verify that the domain assignment matches for all existing test chemicals.

The 5dToxReport web application currently uses workarounds to handle non-genomics data. As BMDExpress gains native support for your data domains, the report generation will become more reliable — no more guessing which organ a dataset belongs to from the filename.

You should see improved accuracy in section headings, table labels, and BMD summary organization once domain identity is carried natively in the data.
